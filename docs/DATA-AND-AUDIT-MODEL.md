# Data and audit model

## Canonical entities

For each entity define its owner, stable identity, required fields, schema/version,
source of truth, and allowed references.

| Entity | Owner and stable identity | Required fields | Schema/version and source of truth | Allowed references |
|---|---|---|---|---|
| `Game` | Product; generated UUID that does not change when titles or editions are corrected | Korean display title, original display title, lifecycle state | Domain schema `game/v1`; PostgreSQL | May be referenced by aliases, releases or platform links, observations, aggregates, and audit events |
| `GameAlias` | Product; generated UUID | Game UUID, locale, original text, normalized text, alias type, priority | `game-alias/v1`; PostgreSQL | References exactly one game |
| `Platform` | Product; stable controlled code plus generated UUID | Code, display label, lifecycle state | `platform/v1`; PostgreSQL | May be referenced by observations and aggregates |
| `PlaytimeObservation` | Product; generated UUID plus unique operation UUID and payload fingerprint | Game UUID, platform UUID, completion scope, positive whole-minute duration, provenance identity, observation date, moderation state | `playtime-observation/v1`; PostgreSQL | References one game, one platform, one operator, and later moderation decisions; may be included by aggregate revisions only when approved |
| `ModerationDecision` | Product; generated UUID | Observation UUID, operator UUID, decision, reason code, decided-at time | `moderation-decision/v1`; PostgreSQL | References one observation and one operator; immutable after creation |
| `PlaytimeAggregateRevision` | Product; aggregate-key hash plus monotonically increasing revision number, also represented by generated UUID | Game UUID, platform UUID, completion scope, rule revision, median minutes, sample count, ordered included-observation UUIDs, calculated-at time, state | `playtime-aggregate/v1` using rule `median-v1`; PostgreSQL | References exactly one game, one platform, and at least three approved observations; may supersede one prior revision |
| `AuditEvent` | Product; generated UUID | Actor identity, operation UUID, entity type and stable identity, action, input hash, outcome, timestamp, created aggregate revision when applicable | `audit-event/v1`; append-only PostgreSQL table | May reference project-owned entities; never contains credentials or unapproved copied source bodies |
| `OperatorAccount` | Project owner through Django authentication; Django user UUID or stable user ID | Login identity, active state, authorization role | Django 5.2 authentication schema plus project role revision `operator/v1`; PostgreSQL | Referenced by decisions and audit events; not exposed publicly |

## State and invariants

- State machine or lifecycle: Games and platforms are `draft`, `active`, or `retired`. Observations are `draft`, `approved`, or `rejected`; approved and rejected observations are immutable. An aggregate key is `insufficient_data` until at least three eligible observations exist, then has one `current` revision; prior revisions become `superseded`, and a current revision may become `retired`.
- Cross-entity invariants: Every alias, observation, decision, and aggregate references existing canonical parents. Observation minutes are positive whole numbers. Completion scope is one of the fixed MVP values. An aggregate includes only approved observations with exactly matching game, platform, and completion scope. Included observation identities are unique. The stored median and sample count are reproducible from the included set under `median-v1`. At most one current revision exists per aggregate key.
- Concurrency and ordering rules: Approval locks the observation and aggregate key, checks duplicate fingerprints, marks the observation approved, recomputes the eligible ordered set, and creates or supersedes an aggregate revision in one transaction. Unique constraints cover normalized alias scope, operation UUID, observation fingerprint, and one-current-revision-per-key. Database UTC time defines event order; client time is evidence only.
- Validation and rejection behavior: Missing provenance or observation date, non-positive or non-integer minutes, unsupported completion scope, invalid parent identity, conflicting operation UUID, duplicate normalized alias within the same scope, duplicate observation fingerprint, or attempt to mutate an approved observation is rejected with a stable code. Fewer than three eligible observations is not an error; it produces the explicit `insufficient_data` state and no public median.

## Side effects and idempotency

The MVP has no remote mutation. Its retryable side effects are local PostgreSQL writes initiated by an authenticated operator. Each form operation carries a generated operation UUID, and each observation stores a normalized fingerprint across game, platform, completion scope, duration, provenance identity, and observation date. Replaying the same UUID and payload resolves to the original receipt and audit-event identity; reusing the UUID with different input is rejected. An exact fingerprint duplicate is rejected and never counted twice. Approval, aggregate recomputation, revision creation, current-pointer update, and audit receipt are atomic. Process interruption before commit leaves no accepted changes; interruption after commit is recovered by reading the operation receipt. Public `GET` requests are side-effect free.

## Audit model

Every authenticated state-changing attempt records or resolves to an append-only `AuditEvent`. The event records stable actor identity, operation UUID, target identity, action, contract and aggregation-rule revisions, immutable input hash, database UTC timestamp, outcome, stable failure code when rejected, and created aggregate revision when successful. The MVP operator is both decision maker and executor, so approval and calculation are fields of one atomic audited operation; a future separation of duties must split them into linked decision and execution events. Successful approval, rejection, supersession, and retirement events commit with affected state. Authorization failures are recorded in a security log without credentials. Validation failures retain codes and hashes instead of raw sensitive input. Audit rows and approved observations are append-only; corrections create new records. Passwords, session tokens, secret values, copied unapproved source bodies, and confidential headers are always redacted.

## Data classification and lifecycle

- Public, internal, confidential, personal, financial, or regulated data: Public data is the approved game identity, aliases selected for display, platform, completion scope, aggregate median, sample count, rule revision, and aggregate revision. Internal data is drafts, provenance details not selected for display, moderation reasons, raw operator-entered observations, superseded revisions, operation identities, and audit evidence. Confidential data is credentials, secret configuration, and private deployment information. Personal data is limited to the operator account identity in the MVP. Financial and regulated player data are not applicable because there is no payment, account, behavioral profile, or health data collection.
- Retention and deletion: Approved observations, aggregate revisions, and audit evidence are retained for the life of the project so displayed values remain reproducible. Retirement removes a game or aggregate from current display but does not erase history. The MVP has no hard-delete operation for approved observations or audit events. A production retention and account-deletion policy must be approved before collecting public user data.
- Backup and recovery: Before any destructive migration or manual data repair, a PostgreSQL backup is required and a restore must be demonstrated in a disposable local environment. Synthetic observations may be recreated from fixtures; the first real game and observation set must be included in backup verification. Production backup schedules and recovery objectives are deferred because production deployment is outside the MVP.
- Migration and backward compatibility: Django migrations are the only schema authority. A migration that removes or rewrites observations, included-observation sets, aggregates, or audit data requires a human checkpoint, backup, dry run, deterministic recalculation comparison, and documented rollback or restore path. Astro and Django are released from one repository against `public-api/v1`; incompatible changes require a new API revision or coordinated migration with contract tests.
- Fixture and log redaction policy: Automated fixtures use synthetic games, provenance URNs, durations, and operator identities. Real credentials, cookies, tokens, private source content, personal play histories, and public-user data are forbidden in fixtures, screenshots, and logs. Logs may contain stable entity and correlation identities, action names, rule revisions, outcomes, and redacted error codes only.
