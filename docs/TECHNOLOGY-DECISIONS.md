# Technology decisions

Technology follows the product contract. Record why each choice is the smallest
adequate option for the first closed loop.

## Runtime and repository layout

- Language/runtime and exact supported versions: Node.js 22.x with Astro 7.x and TypeScript 5.x for the public web application; Python 3.12.x with Django 5.2.x LTS for canonical data, operator workflows, aggregation, and the read API; PostgreSQL 17.x for persistence. Patch releases are advanced within these fixed major/minor lines through reviewed lock-file updates.
- Package/build tool and lock strategy: The Astro application uses npm and a committed `package-lock.json`; CI and local verification use `npm ci`. The Django application uses `uv` with a committed `uv.lock` and Python constrained to 3.12.x. Direct dependencies are declared once and transitive versions remain lock-file controlled. Container image digests used in verification are pinned when introduced.
- Repository layout: One repository with `apps/web` for Astro, `apps/backend` for Django, `contracts/public-api/v1` for checked-in interface schemas and examples, `docs` for these contracts, and `infra/local` for local-only container configuration. Domain ownership and calculation stay in Django; Astro contains no canonical write or playtime aggregation logic.
- Local development environment: Host Node.js 22.x and Python 3.12.x run the applications; Docker Compose v2 runs PostgreSQL 17.x on a private local network. A committed example environment file lists required variable names without values. The MVP must run without a cloud account.

## Application architecture

- Primary components and responsibilities: Astro performs public routing, title search presentation, accessibility, and server-side calls to the read API. Django owns authentication, forms, canonical identity, validation, moderation, duplicate rules, `median-v1` calculation, aggregate revisioning, audit events, migrations, and versioned JSON reads. PostgreSQL is the only canonical source of truth. Generic framework features are used instead of reimplementation.
- Persistence and transaction boundary: All canonical writes and aggregate calculations go through Django and one PostgreSQL database. Final observation approval, aggregate revision creation or insufficient-data result, current-revision update, and audit event are one database transaction. Astro has no write connection and no independent data store.
- Interface style and schema mechanism: Operator mutation uses Django session-authenticated HTML forms. Public reads use HTTP JSON under `/api/v1`; checked-in JSON Schema and representative fixtures define the contract, and live contract tests verify Django output and Astro consumption. Public URLs use product-owned stable identifiers or slugs; titles and store identifiers are aliases only.
- Background, scheduled, or concurrent work: No background worker, scheduler, cache, queue, crawler, or asynchronous aggregation is added to the first loop. Approval recalculates the one affected aggregate key synchronously. Bulk recalculation and contribution ingestion are later decisions.

## Dependencies

- Preferred existing capabilities: Django authentication, sessions, CSRF, forms, administration, ORM, migrations, and database transactions; Astro routing and server rendering; PostgreSQL constraints, indexes, and aggregate expressions; Python's deterministic statistics support or a small reviewed equivalent; standard browser APIs; and open-source test tools. The product implements only game normalization, provenance, moderation, eligibility, aggregation, publication, and audit rules.
- Dependencies that must be pinned rather than copied/forked: Astro, Django, the PostgreSQL driver, JSON Schema validation tooling, test runners, browser-test tooling, and any normalization or statistics library accepted later. Their source is not copied into the repository except for license notices or generated lock metadata.
- Forbidden or unreviewed dependencies: Unlicensed game or playtime datasets, private or reverse-engineered interfaces, automated scraping packages, proprietary game SDKs, external authentication, price/store/catalog APIs, analytics, advertising, payment, queues, caches, or UI kits are forbidden until a dedicated decision records need, data behavior, license, privacy, and rollback. Unknown-license and AGPL dependencies require explicit owner approval before addition.
- License and advisory acceptance process: Before adding or updating a direct dependency, record its package identity, pinned version, SPDX license, advisory result, data or network behavior, and why existing capabilities are insufficient. Unknown, incompatible, abandoned, or critical-vulnerability dependencies block the change. Patch updates remain reviewable lock-file commits and must pass the repository gate.

## Verification technology

- Focused test tools: Django's test framework or pytest with pytest-django for canonical constraints, state transitions, authorization, idempotency, transactions, and deterministic median calculations; property-style cases for odd and even sample counts; Vitest for isolated Astro behavior; JSON Schema validation for API fixtures; and Playwright for public browser flows. Selected runner versions are pinned in their lock files.
- Repository gate: Frozen dependency installation; Python formatting and static checks selected during bootstrap; `python manage.py check`; migration drift check; backend unit and integration tests; deterministic aggregate replay tests; API schema tests; Astro type/content checks; frontend tests; production builds for both applications; and the Playwright closed-loop scenario. Exact commands become repository scripts before feature work and run from a clean checkout.
- External integration or viability environment: No third-party sandbox is required. The smallest real interface environment is local multi-process integration: Astro 7, Django 5.2, and PostgreSQL 17 communicate over real HTTP and database connections with synthetic data, followed by one manual owner-approved real game and observation set.
- Secret, license, schema, migration, and compatibility checks: Secret scanning covers source, fixtures, logs, and built assets; direct and transitive licenses and advisories are reviewed; JSON Schema compatibility is checked on producer and consumer; Django reports no uncommitted model changes; aggregate results are replayed from included observation identities; forward migration and backup-based recovery are tested for destructive changes; and the Astro build is inspected to ensure no backend secret is exposed.

## Environments and deployment

- Local, test, preview, and production boundaries: Local development may use operator-created real observations only after human source approval. Automated tests use synthetic data and isolated databases. Preview, if created, uses synthetic or explicitly approved non-sensitive data and separate secrets. Production is not an MVP completion requirement and no production-readiness claim may be made from local or preview evidence.
- Configuration and secret injection: Runtime configuration is supplied through environment variables or an owner-controlled secret mechanism. Only documented public configuration may cross into Astro client code. Database credentials, Django secret key, operator bootstrap values, and deployment credentials remain server-side and are never committed.
- Production setup deferred from MVP: Domain and trademark checks, hosting provider, TLS termination, reverse proxy, CDN, production database, backups and recovery objectives, monitoring, rate limiting, abuse controls, 2FA, analytics, consent and privacy review, public accounts and submissions, moderation staffing, charts, email, advertising, affiliate links, payment, external game/store/catalog APIs, bulk recalculation, and disaster recovery.
